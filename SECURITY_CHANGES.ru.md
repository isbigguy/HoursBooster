# Более безопасная версия vaporBooster — v0.0.2

Основа: `valnssh/vaporBooster`, коммит `cc1e8f3b9179b70ca455cfdca63cabab3a550cfd`.

## Изменения

- Нативный HTTPS обязателен. Нет HTTP fallback; без сертификата и ключа сервер
  не запускается. Требуются совпадающие HTTPS `BETTER_AUTH_URL` и `ORIGIN`.
- Cookies авторизации всегда `Secure`; HSTS добавляется к ответам панели,
  статики и ошибок. Сертификаты исключены из Git, Docker build и Vite-раздачи.
- Для Steam включён `webCompatibilityMode`: библиотека выбирает только WSS
  на порту 443. Сырой TCP-транспорт исключён из входа по паролю/токену.

- Веб-панель получает только разрешённые поля аккаунта. Steam Guard seed,
  refresh token, IV/tag и полная auth-сессия не сериализуются в браузер.
- Все действия с аккаунтом проверяют владельца. Без OIDC доступны только
  аккаунты с `userId = null`, а общий режим требует явного `ALLOW_ANONYMOUS=true`.
- Частичная конфигурация OIDC и слабый master secret блокируют запуск.
- Подтверждения удаления выводятся как текст, без `@html` для пользовательских имён.
- QR-вход хранит владельца с момента создания, ограничен 16 сессиями на процесс
  и двумя на владельца, имеет TTL 120 секунд и отмену. События обрабатываются
  независимо от polling; результат можно потребить только один раз.
- В `patches/steam-session@1.9.4.patch` исправлена отмена незавершённого
  WebSocket-подключения библиотеки: отменённая попытка больше не переподключается.
  Собственный HTTPS agent каждой QR-сессии уничтожается при завершении.
- Новые токены и 2FA seeds шифруются AES-256-GCM с версионированием. Старые
  токены читаются прежним алгоритмом; plaintext seeds всех аккаунтов
  мигрируют при инициализации. Пароли Steam остаются временными аргументами входа.
- Повреждённый seed отклоняется только для своего аккаунта (`LOGIN_REQUIRED`),
  без блокировки панели и удаления других аккаунтов. Он не трактуется как plaintext.
- Удалены Google Fonts, интеграция SteamDB и вывод содержимого чата в stdout.
  Better Auth telemetry явно выключена. История чата по-прежнему хранится в БД
  для штатного интерфейса; доступ к БД и её резервным копиям нужно ограничивать.
- Зависимости обновлены и зафиксированы lockfile и точными версиями.
  Для старых транзитивных зависимостей Steam установлены целевые overrides;
  их используемые protobuf/ZIP API проверяются регрессионным тестом.
- Docker не включает `.env` и SQLite из build context, не выполняет миграцию
  во время сборки и не копирует БД в образ. Runtime создаёт/мигрирует БД в volume.
- Compose публикует только HTTPS 443, по умолчанию на `127.0.0.1`. Контейнер запускается как `deno`,
  без capabilities, с read-only root filesystem и отдельным `/data`.
  У Deno нет `--allow-run` и общего `-A`; чтение/запись ограничены путями.

## Запуск и перенос данных

1. Скопируйте `example.env` в `.env`, задайте случайный `BETTER_AUTH_SECRET`
   длиной не менее 32 символов и свой HTTPS-домен в `BETTER_AUTH_URL` и `ORIGIN`.
   Предоставьте сертификат и приватный ключ по инструкции `DEPLOY_DEBIAN13.ru.md`.
2. Настройте четыре обязательных OIDC-параметра. Для отдельного доверенного
   локального экземпляра можно явно установить `ALLOW_ANONYMOUS=true`;
   не открывайте этот режим посторонним.
3. После обновления Better Auth зарегистрируйте у провайдера callback:
   `<BETTER_AUTH_URL>/api/auth/callback/<OIDC_PROVIDER_ID>`.
4. Перед переносом остановите старую версию и сохраните резервную копию БД.
   Не меняйте прежний сильный `BETTER_AUTH_SECRET`: он нужен для чтения старых токенов.
   При Docker-развёртывании перенесите SQLite в volume как `/data/sqlite.db`,
   назначив владельцем пользователя `deno`. Не кладите рабочую БД внутрь образа.
5. Запустите `docker compose up --build -d`. Для обычной установки используйте
   Node 24, Deno 2.9.8, `pnpm install --frozen-lockfile --ignore-scripts`,
   `pnpm migrate`, `pnpm build`, `pnpm start`.
   На Windows без права создания symlink установка может требовать `--node-linker=hoisted`.

Шифрование при миграции не стирает старый plaintext из уже существующих backups,
свободных SQLite pages или снапшотов. Смена master secret требует отдельного
перешифрования либо повторного входа в аккаунты.

## Проверки и границы

`pnpm test` выполняет регрессионные проверки на временной SQLite и fake Steam
sessions. Настоящие Steam credentials не используются. Также предусмотрены
`pnpm check`, `pnpm lint`, `pnpm build`.

В этой среде проверен production runtime в Deno с ограниченными разрешениями:
инициализация новой БД, HTTPS-ответ панели, заголовок `no-store`, отсутствие
Google Fonts/SteamDB и отказ действия для неизвестного аккаунта.
Docker engine недоступен, поэтому Linux-образ и Compose здесь не запускались.
Вход в настоящий Steam и в реальный OIDC provider не проверялся.

После обновлений npm audit не показывает high/critical advisories. Оставшиеся
предупреждения низкой тяжести для SvelteKit 2/deepmerge требуют отдельной оценки;
переход на SvelteKit 3 не выполнен, поскольку Deno-адаптер заявляет peer `2.x`.
Это не утверждение, что эти предупреждения никогда не применимы.

Приложению необходим исходящий доступ к Steam, DNS и настроенным OIDC/DB.
Разрешение `--allow-net` не является списком допустимых адресов. Нативный SQLite
addon требует FFI, поэтому флаги Deno не дают полной изоляции от злонамеренной
нативной зависимости. Контейнерные ограничения также не заменяют отдельный
контроль трафика и проверку образа перед публичным развёртыванием.
